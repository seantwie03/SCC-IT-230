Exercise

Build the App Tier Exercise

Task

Make servera Forgejo's app tier. Run Forgejo in a rootless container, as a service of a user of its own, with all of its data on serverb: its files on the NFS share from Build the Data Tier, automounted on servera, and its database in PostgreSQL. The next exercise, Build the Web Tier, puts httpd in front of Forgejo, so leave servera as this exercise ends.

Host
servera
Prerequisite
Build the Data Tier

  1. Install Podman, autofs, and the NFS client

    Log in to servera as student. This exercise uses sudo where it needs root. autofs does not bring nfs-utils, which holds the program that mounts NFS shares, so install all three: 

    ssh servera
sudo dnf install -y podman autofs nfs-utils

    The install prints two warnings that gssproxy.service changed on disk, which you can ignore.

  2. Create the user forgejo, with UID 2000, a password, and lingering

    Forgejo's files on serverb belong to UID 2000, and NFS keeps owners as UIDs, so create forgejo with the same UID here: 

    sudo useradd -u 2000 forgejo
sudo passwd forgejo

    Enter redhat twice. passwd warns that it is short and sets it anyway, because root asked: 

    New password:
BAD PASSWORD: The password is shorter than 8 characters
Retype new password:
passwd: password updated successfully

    Lingering starts forgejo's services at boot and keeps them running after it logs out: 

    sudo loginctl enable-linger forgejo
loginctl list-users
     UID USER    LINGER STATE
1000 student no     active
2000 forgejo yes    lingering

2 users listed.

  3. Automount Forgejo's files from serverb on forgejo's ~/data

    Build the Data Tier opened rpc-bind and mountd on serverb, so showmount can list its exports: 

    showmount --exports serverb
    Export list for serverb:
/srv/forgejo servera.lab.example.com

    Mount the share with a direct map. First, a master map file that names the map, with /- for a direct map: 

    sudo vim /etc/auto.master.d/forgejo.autofs

    Press i and type:

    /-  /etc/auto.forgejo

    Press Esc, then type :wq and press Enter. Then the map itself, which gives the full path of the mount point, its options, and the share: 

    sudo vim /etc/auto.forgejo

    Press i and type:

    /home/forgejo/data  -rw,sync  serverb.lab.example.com:/srv/forgejo

    Press Esc, then type :wq and press Enter. Start autofs and look at what is mounted: 

    sudo systemctl enable --now autofs
mount | grep forgejo
    Created symlink '/etc/systemd/system/multi-user.target.wants/autofs.service' → '/usr/lib/systemd/system/autofs.service'.
/etc/auto.forgejo on /home/forgejo/data type autofs (rw,relatime,fd=12,pgrp=2803,timeout=300,minproto=5,maxproto=5,direct,pipe_ino=16250)

    Only the autofs trigger is there: nothing from serverb yet. Looking inside the mount point mounts the share. forgejo's home is private, so use sudo: 

    sudo ls -la /home/forgejo/data
mount | grep forgejo
    total 0
drwxr-xr-x. 2 forgejo forgejo   6 Nov 21 17:09 .
drwx------. 4 forgejo forgejo 103 Nov 21 17:20 ..
/etc/auto.forgejo on /home/forgejo/data type autofs (rw,relatime,fd=12,pgrp=2803,timeout=300,minproto=5,maxproto=5,direct,pipe_ino=16250)
serverb.lab.example.com:/srv/forgejo on /home/forgejo/data type nfs4 (rw,relatime,sync,vers=4.2,rsize=262144,wsize=262144,namlen=255,hard,proto=tcp,timeo=600,retrans=2,sec=sys,clientaddr=172.25.250.10,local_lock=none,addr=172.25.250.11)

    The nfs4 mount from serverb now sits below the trigger. Your dates and the numbers in the autofs line may differ.

  4. Run Forgejo in a container as the forgejo user

    Log in as forgejo with SSH:

    ssh forgejo@servera

    Enter forgejo's password, redhat. If SSH asks whether to trust servera's host key, answer yes.

    Log in with SSH, not su Only a login session gives forgejo a systemd of its own, which step 6 needs. su - forgejo and sudo -iu forgejo do not start one.

    Run Forgejo. Type the command on several lines, each ending in \, or on one line without them: 

    podman run -d --name forgejo --network host --userns keep-id:uid=1000,gid=1000 \
-v ~/data:/var/lib/gitea:Z \
-e FORGEJO__server__ROOT_URL=http://git.lab.example.com/ \
-e FORGEJO__security__INSTALL_LOCK=true \
-e FORGEJO__database__DB_TYPE=postgres \
-e FORGEJO__database__HOST=serverb.lab.example.com:5432 \
-e FORGEJO__database__NAME=forgejo \
-e FORGEJO__database__USER=forgejo \
-e FORGEJO__database__PASSWD=redhat \
codeberg.org/forgejo/forgejo:15-rootless

    Its options, in order:

    • --network host uses servera's own network, so Forgejo listens on servera's ports 3000 and 2222 with no -p, and reaches serverb from servera's address.
    • --userns keep-id:uid=1000,gid=1000 keeps the ID of the user running Podman, forgejo (UID 2000), and gives it to UID 1000 inside the container, the git user that runs Forgejo. So Forgejo's files on serverb belong to forgejo; without it, Forgejo cannot write them.
    • -v ~/data:/var/lib/gitea:Z gives Forgejo the automounted share as its data directory.
    • Each -e FORGEJO__section__KEY becomes KEY in the [section] of Forgejo's configuration file, app.ini: ROOT_URL is the address Forgejo puts in its links, INSTALL_LOCK skips its install page, and the database lines point it at PostgreSQL on serverb, with the password from Build the Data Tier.
    • The -rootless image of version 15, Forgejo's long-term-support line, runs Forgejo as a regular user from the start. The standard image changes its files' owner as it starts, which NFS refuses.

    Podman pulls the image, printing its progress, then the new container's ID. The pull and Forgejo's first start can take half a minute. 

    Trying to pull codeberg.org/forgejo/forgejo:15-rootless...
Getting image source signatures
...output omitted...
Writing manifest to image destination
c3ceedb0717c1a75e7a4b265c2f8b8bfcfeccd8a9a7e69978382a8e58882ccc9

    Check the container, then Forgejo's home page:

    podman ps
curl -s localhost:3000 | grep '<title>'
    CONTAINER ID  IMAGE                                     COMMAND     CREATED         STATUS         PORTS               NAMES
c3ceedb0717c  codeberg.org/forgejo/forgejo:15-rootless              22 seconds ago  Up 20 seconds  2222/tcp, 3000/tcp  forgejo
	<title>Forgejo: Beyond coding. We forge.</title>

    If curl prints nothing, Forgejo is still starting. Wait a few seconds and run it again.

  5. Create Forgejo's first admin

    INSTALL_LOCK skipped Forgejo's install page, so make the first admin from a shell inside the container: 

    podman exec -it forgejo /bin/bash

    The prompt changes to servera:/var/lib/gitea$: this shell runs inside the container, as Forgejo's own user, git. Create the admin with Forgejo's command-line tool, then leave the container: 

    forgejo admin user create --admin --username student --password student --email student@lab.example.com
exit
    New user 'student' has been successfully created!

    Like every Forgejo account, the new admin is stored in PostgreSQL on serverb.

  6. Run the container as a user service that starts at boot

    Back at forgejo's prompt, make the directory for its own units and generate one for the container: 

    mkdir -p ~/.config/systemd/user
cd ~/.config/systemd/user
podman generate systemd --new --files --name --restart-sec 10 \
--wants podman-user-wait-network-online.service \
--after podman-user-wait-network-online.service forgejo
    DEPRECATED command:
It is recommended to use Quadlets for running containers and pods under systemd.

Please refer to podman-systemd.unit(5) for details.
/home/forgejo/.config/systemd/user/container-forgejo.service

    The notice is expected; the command still works. --restart-sec 10 is new: at boot, nothing makes autofs mount ~/data before this service starts. If the service starts first, it fails, and without the option systemd retries after 100 ms and gives up after five tries in ten seconds. With it, systemd retries every 10 seconds, which never reaches that limit, so Forgejo starts once its data is there.

    --new makes the service create its own container, so remove this one. Its data stays on serverb. 

    podman rm -f forgejo
systemctl --user daemon-reload
systemctl --user enable --now container-forgejo
curl -s localhost:3000 | grep '<title>'
    forgejo
Created symlink '/home/forgejo/.config/systemd/user/default.target.wants/container-forgejo.service' → '/home/forgejo/.config/systemd/user/container-forgejo.service'.
	<title>Forgejo: Beyond coding. We forge.</title>

    Log out of forgejo, and check the page again as student: 

    exit
curl -s localhost:3000 | grep '<title>'
    	<title>Forgejo: Beyond coding. We forge.</title>

    forgejo has logged out, and lingering keeps its service running. Leave servera as it is: Build the Web Tier puts httpd in front of port 3000.
