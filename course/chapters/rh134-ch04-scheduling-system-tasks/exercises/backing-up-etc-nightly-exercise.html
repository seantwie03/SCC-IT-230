Backing Up /etc Nightly Exercise

Task

Back up /etc every night at 10 p.m. as root, on two machines with very different habits. servera is a server that never sleeps, so a system crontab suits it. Treat workstation as a laptop that is closed at 10 p.m., and give the same script to anacron instead.

Hosts
servera, then workstation
Back up
/etc
Runs as
root
Schedule
every night at 10 p.m.

  1. Write the backup script on servera

    Log in to servera and become root, because everything in this exercise is system-wide. 

    sudo -i
vim /usr/bin/etc_backup.sh

    Press i and write two lines, then leave insert mode with jj and save with :wq. 

    #!/bin/bash
tar -caf /tmp/etc_$(date --iso-8601=minutes).tar.gz /etc 2>/dev/null

    Make it executable and run it once by hand. Never hand a schedule a command you have not run yourself. 

    chmod a+x /usr/bin/etc_backup.sh
etc_backup.sh
ls -l /tmp/etc_*.tar.gz
    Why the name alone works /usr/bin is already on root's PATH, so the script runs without a leading ./ or a full path.

  2. Schedule it in /etc/cron.d

    Copy /etc/crontab into /etc/cron.d/ as a starting point. You get the field reference in the comments, and you leave the original file untouched. 

    cp /etc/crontab /etc/cron.d/backups
vim /etc/cron.d/backups

    Press G to reach the last line and o to open a new one below it. Add a test schedule that runs every minute, then save. 

    * * * * * root /usr/bin/etc_backup.sh
    The extra field A system crontab has root between the five time fields and the command. Your own crontab has no such field, because every job in it already runs as you.

  3. Confirm root ran it

    Wait for the next minute to tick over, then read the log and look for a new archive. 

    grep etc_backup /var/log/cron
ls -l /tmp/etc_*.tar.gz

    The log names the user the job ran as:

    CROND[12124]: (root) CMD (/usr/bin/etc_backup.sh)
CROND[12123]: (root) CMDEND (/usr/bin/etc_backup.sh)

  4. Set the real 10 p.m. schedule

    The job works, so give it the schedule you actually want. Press G for the last line and cc to replace it. 

    vim /etc/cron.d/backups
    0 22 * * * root /usr/bin/etc_backup.sh

    Save, then read the last line back to confirm it.

    tail -1 /etc/cron.d/backups

  5. Give the same script to anacron on workstation

    That schedule is fine for a server. Now treat workstation as a laptop: closed and asleep at 10 p.m., so a crontab entry would simply never fire. Leave the root shell, connect, and become root there. 

    exit
ssh workstation
sudo -i

    Write the same script, but into /etc/cron.daily/, and make it executable. A script that is not executable is silently ignored. 

    vim /etc/cron.daily/etc_backup.sh
    #!/bin/bash
tar -caf /tmp/etc_$(date --iso-8601=minutes).tar.gz /etc 2>/dev/null
    chmod a+x /etc/cron.daily/etc_backup.sh
    No schedule to write There are no time fields here. You are asking for "about once a day" and letting anacron pick the moment.

  6. Let anacron catch up

    Anacron records the date it last ran each group of jobs. Look at that date, then ask anacron to run anything overdue. 

    cat /var/spool/anacron/cron.daily
anacron -n
ls /tmp/etc_*.tar.gz

    Nothing happened, because today's daily job is not overdue. Now pretend the laptop has been closed since January and ask again. 

    echo 20260101 > /var/spool/anacron/cron.daily
anacron -n
ls -l /tmp/etc_*.tar.gz
cat /var/spool/anacron/cron.daily

    The backup ran, and the recorded date has caught up to today. That is the whole point: the job was missed, and anacron noticed.

  7. Clean up both hosts

    Remove the laptop side first, while you are still on it. 

    rm -f /etc/cron.daily/etc_backup.sh /tmp/etc_*.tar.gz
exit
exit

    Those two exit commands drop the root shell and then the ssh session, leaving you back on servera. Remove the server side there. 

    sudo rm -f /etc/cron.d/backups /usr/bin/etc_backup.sh /tmp/etc_*.tar.gz
ls /etc/cron.d/
